# Проверка Compose UI по макету

Методика для проверки расположения элементов, ресурсов и стилей экрана PureAndroid при ревью или прямом запросе на сверку UI.

## Источник Figma — открытый вопрос

**Ссылка на Figma UI kit и макеты пока не задана.** При каждом новом запросе с упоминанием Figma, пока нужных данных нет, напомни об открытом вопросе и предложи два варианта.

- **A — добавить ссылку.** Получи ссылку на UI kit и конкретный `node-id` экрана или варианта компонента. Если предоставлен только файл с несколькими похожими фреймами, уточни нужный узел.
- **B — пропустить.** Пропусти сравнение с Figma в текущей задаче, выполни доступную проверку по коду и отметь её границы в результате. В следующих задачах вопрос задаётся снова, пока источник остаётся открытым.

После получения ссылки используй точный узел и согласованное состояние экрана. Если данные Figma недоступны, уточни дальнейшие действия. Независимую проверку исходников можно продолжать во время ожидания.

Согласованные параметры перенесены из TBI — ширина эталонного макета 375, `1 px` макета соответствует `1 dp` Compose. Для стандартного Preview без параметра `device` исходная конфигурация имеет ширину 411 dp и плотность 2.625. Перед измерением проверь фактическую конфигурацию рендера. Расхождение с этими параметрами требует уточнения условий сравнения.

## Отступы и размеры

1. Пройди макет сверху вниз и выпиши все вертикальные отступы, включая верхний отступ первого элемента, `padding` каждого вложенного контейнера и `gap` между детьми. Для горизонтальных рядов повтори расчёт по горизонтали. `gap-[14px]` в коде дизайн-контекста задаёт расстояние по обеим осям.
2. Сопоставь каждую величину с конкретным `padding`, `Arrangement.spacedBy`, spacer-функцией или `contentPadding` списка. Учти вклад каждого вложенного контейнера ровно один раз. Для дополнительного отступа установи причину и применимое соглашение проекта.
3. Для промежутка между элементами найди ближайший общий контейнер. Сложи нижние отступы на стороне первого элемента, верхние на стороне второго, размеры spacer-элементов и `spacedBy(k)` за каждую пересечённую границу соседних детей.
4. `Spacer` сам является ребёнком контейнера. Между обычными элементами с промежуточным `VSpacer(h)` в `Column` с `spacedBy(k)` расстояние составляет `k + h + k`. Например, при `k = 8.dp` и `h = 16.dp` получится 32 dp. Дополнительный нижний padding предыдущего вложенного контейнера в 16 dp увеличит расстояние до 48 dp.
5. Пометь размеры с `weight` и `fillMax*` как зависящие от доступного пространства. Проверь переносы текста, ограничения родителя и порядок модификаторов. Совпадение на ширине 375 оценивай вместе с поведением при других размерах.
6. Отдельно учти системные insets и нижнюю панель. В PureAndroid экраны используют `WindowInsets.safeDrawing`, а [`NavigationBarSceneDecoratorStrategy`](../feature/app/src/main/kotlin/ru/sla/pure/android/feature/app/NavigationBarSceneDecoratorStrategy.kt) потребляет нижний inset для контента сцены с панелью. Проследи всю цепочку применения и потребления insets.
7. Сохраняй завершающий отступ прокручиваемого контента как указание конца списка, даже когда в макете он отсутствует. В прокручиваемом `Column` используй `VSpacer`, в lazy-списке учитывай эквивалентный нижний `contentPadding`. Этот намеренный отступ учитывай отдельно при сравнении с макетом.

## Spacer-функции PureAndroid

Используй [Spacers.kt](../uikit/src/main/kotlin/ru/sla/pure/android/uikit/spacer/Spacers.kt) в экранах и компонентах для вертикального, горизонтального и гибкого промежутка.

```kotlin
import ru.sla.pure.android.uikit.spacer.HSpacer
import ru.sla.pure.android.uikit.spacer.VSpacer
import ru.sla.pure.android.uikit.spacer.WSpacer

VSpacer(16.dp)
HSpacer(8.dp)
// Inside ColumnScope or RowScope.
WSpacer(1f)
```

`WSpacer` имеет отдельные реализации для `ColumnScope` и `RowScope`. Для промежутков с `height`, `width` и `weight` используй эти функции вместо прямого вызова `Spacer`.

## Измерения через Android Studio

- Используй [Android CLI](android-studio-cli.md), когда `studio check` показывает PureAndroid как `READY`, а сборка в Studio соответствует проверяемому коду. При неизвестной актуальности сборки уточни её или ограничь результат анализом исходников. Запуск сборки регулируют [правила проекта](code-quality.md).
- `render-compose-preview --print-semantics` возвращает дерево семантики с границами и сохраняет PNG. Задавай `--output-image-file` во временной папке. Для числовой проверки достаточно границ элементов, присутствующих в дереве.
- При согласованной плотности 2.625 переводи границы из px в dp делением на 2.625. Зазор равен верхней границе следующего элемента минус нижняя граница предыдущего в общей системе координат. Сравнивай с геометрией конкретного узла Figma.
- Учитывай ширину Preview 411 dp относительно эталона 375 и различия демонстрационных текстов. Для фиксированных размеров и отступов проверяй сопоставимость ограничений. Высоту текста и адаптивные размеры сверяй при одинаковых условиях.
- Проверь, какую аннотацию `@Preview` обработал инструмент. В исходной процедуре отрисовывалась первая, Light. В PureAndroid текущие Preview используют `AppTheme`, поэтому фиксируй фактически выбранную тему и полноту проверки вариантов.

## Изображения и визуальная проверка

- По умолчанию проверь существование drawable или другого ресурса и соответствие его назначения макету. Назови результат «ресурс проверен по ссылке и назначению» и укажи, выполнялось ли визуальное сравнение.
- Перед переходом к визуальной проверке рендера спроси пользователя, требуется ли она. Учитывай уже данное разрешение на такую проверку в текущей задаче.
- Для визуального сравнения открой реальный рендер drawable или Compose Preview и изображение того же узла Figma. Проверь форму, масштабирование, обрезку и тему. Вывод о совпадении изображения основывай на просмотре обеих картинок.

## Типографика, цвета и компоненты Material 3

- Сопоставь стиль Figma с ролью в [`AppTypography`](../uikit/src/main/kotlin/ru/sla/pure/android/uikit/theme/AppTypography.kt) — `headline`, `title`, `body`, `bodySmall`, `label`, `caption`. Затем проверь размер, `lineHeight`, насыщенность, шрифт и масштаб текста. Отсутствие однозначного соответствия согласуй с разработчиком.
- Проследи цвет через [`ColorPalette`](../uikit/src/main/kotlin/ru/sla/pure/android/uikit/theme/ColorPalette.kt), [`AppColors`](../uikit/src/main/kotlin/ru/sla/pure/android/uikit/theme/AppColors.kt) и [`AppTheme`](../uikit/src/main/kotlin/ru/sla/pure/android/uikit/theme/AppTheme.kt). `AppTheme` также настраивает `MaterialTheme` для компонентов Material 3. Если роль токена выбрана правильно, а значение расходится, локализуй замечание в палитре или сопоставлении темы.
- Если Figma даёт только hex, ищи точное соответствие токену, по возможности по паре Light/Dark. При неоднозначности спроси разработчика. В результате укажи подбор по значениям и ограничения полученных данных. При расхождении цвета плашки UI kit с её текстовым hex ориентируйся на заливку и сообщи о расхождении.
- Определи компонент и вариант по `componentId` и метаданным Figma, затем сопоставь с компонентом Material 3 и его параметрами. Если компонент отсоединён от UI kit, данные неполные или подходящего токена либо компонента нет, уточни решение. Новые токены и варианты должны опираться на подтверждённый UI kit.
- Проверь `colors`, `shape`, `border`, `enabled`, `contentPadding`, минимальные размеры и область нажатия выбранного компонента. Для варианта с фиксированным дизайном меняй оформление через предусмотренные параметры. Встретив внешнее переопределение через `Modifier.background` или `border`, обсуди его с разработчиком. Фон обычного `Text` оценивай по макету.
- Размер компонента зависит от padding, высоты строк, font padding и ограничений. Учитывай эти вклады отдельно от внешнего отступа в Preview. Проверяй реальную реализацию и используемую версию Material 3.
- Для ошибки фона проследи цепочку от темы окна [`Theme.PureAndroid`](../app/src/main/res/values/themes.xml) и `MainActivity` до `Surface` или `Modifier.background` конкретного экрана. Общая правка палитры затрагивает все использующие её токены.

## Результат

Сначала проверь установившиеся соглашения проекта и их поведение при размере эталона. Замечание о расхождении должно содержать узел Figma, ожидаемую величину, фактический расчёт и точную строку кода. Неподтверждённые места перечисляй как вопросы для проверки. Если в проверенной области расхождений нет, сообщи об этом в общем результате.

Пиши замечания на русском по [формату ревью](review-comment-format.md), сохраняя код и идентификаторы на английском. Отметь выбранный вариант A/B, источник, параметры сравнения, выполненные проверки и оставшиеся ограничения.
