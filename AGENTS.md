# Инструкции для PureAndroid

## Перенос инструкций

- Адаптируй переносимые документы под фактический код, инструменты и соглашения PureAndroid, сохраняя смысл требований. Если для требования отсутствует участок кода, инструмент, правило или другое необходимое основание, спроси разработчика, как с ним поступить, прежде чем удалять, ослаблять или заменять это требование. Продолжай независимые части адаптации, пока ожидаешь ответ.

## Загрузка skills

Тематические инструкции находятся в `.agents/skills/<тема>/SKILL.md`. При соответствующей задаче прочитай указанный skill через механизм skills клиента либо открой файл напрямую. Относительные ссылки внутри skill отсчитываются от его каталога; команды выполняются из корня проекта, если не указано иное.

## DI

- Для прямой привязки реализации к интерфейсу ставь `@ContributesBinding` на класс реализации и указывай скоуп привязки. Например, `MainFlow` предоставляет `Flow` через `@ContributesBinding(MainScope::class)`, а `@SingleIn(MainScope::class)` задаёт один экземпляр на граф главного флоу. Отдельный метод `@Provides`, который только возвращает эту реализацию, избыточен.
- Используй `@ForScope` на привязке и в месте запроса, когда нужно различать зависимости одного типа по скоупу. Metro учитывает тип и квалификатор при поиске зависимости. `@SingleIn` управляет временем жизни экземпляра, поэтому для кэшируемой квалифицированной зависимости нужны обе аннотации. Например, `MainFlowComponent` наследует `flow()` для локальной привязки `Flow`, а для `coroutineScope()` указывает квалификатор `MainScope`.
- Подключай DI-модуль к графу через `@ContributesTo` со скоупом компонента. Например, `MainFlowModule` помечен `@ContributesTo(MainScope::class)`, поэтому `MainFlowComponent` объявляется с `@GraphExtension(MainScope::class)` без `@BindingContainer` на модуле и без списка `bindingContainers` в компоненте.
- Определяй привязки Metro с `@Provides` и `@Binds` в отдельном модуле соответствующего компонента. Например, привязки `AppComponent` принадлежат `AppModule`, а привязки `AppFlowComponent` — `AppFlowModule`. Параметры фабрики, передающие экземпляры в граф при его создании, остаются в фабрике.
- В интерфейсе модуля размещай `@Provides` прямо на методе с реализацией. Для простого провайдера достаточно выражения, например `fun provideCoroutineScope(): CoroutineScope = createCoroutineScope()`.
- Для второго интерфейса того же флоу добавляй в модуль привязку, например `@Binds val MainFlow.bindFlowEventSink: FlowEventSink`. ViewModel экранов Login и Main запрашивают локальный `FlowEventSink` без квалификатора. Обработчик `AppFlow` помечай `@ForScope(AppFlowScope::class)` и на привязке, и во всех местах запроса, включая параметр `appEvents` дочернего флоу.
- Объявляй вложенную `Factory` перед методами компонента. В методе, который возвращает дочернюю фабрику, используй полное имя компонента, например `loginFlowComponentFactory()`. Для фабрик, объединяемых Metro в одном родительском скоупе, выбирай различные сигнатуры создания, например `createLoginFlowComponent()` и `createMainFlowComponent()`: одного различия в возвращаемом типе недостаточно.
- На классе ViewModel пиши `@ViewModelKey`: Metro берёт ключ из аннотированного класса. Для наследников `BaseViewModel` указывай `@ContributesIntoMap(MainScope::class, binding<ViewModel>())` с соответствующим скоупом. Фабрика ищет провайдеры с типом значения `ViewModel`, а при выводе типа Metro возьмёт непосредственный супертип `BaseViewModel<…>`.
- На assisted-фабрике, которая напрямую наследует `ManualViewModelAssistedFactory`, достаточно `@ManualViewModelAssistedFactoryKey` и `@ContributesIntoMap(MainScope::class)` с нужным скоупом: здесь выведенный тип уже совпадает с типом значения карты фабрик.
- Привязки, предназначенные только для тестового графа, вноси через `@ContributesTo(TestAppScope::class)`. Подключай этот скоуп через `additionalScopes` тестового графа и перечисляй в `excludes` производственные модули, которые он заменяет.

## Навигация

- Внутри `flow { ... }` подключай записи вложенного флоу через его `EntryProviderInstaller`. Например, `with(LoginEntryProviderInstaller(appComponent.loginFlowComponentFactory())) { install() }` регистрирует экраны входа в текущем контексте навигации.
- Для панели со своим флоу поверх текущего экрана используй отдельный навигационный хост. Пока панель открыта, сохраняй стек основного хоста, отключай его обработку «Назад» и скрывай его содержимое от сервисов доступности. Кнопку закрытия и системное действие «Назад» направляй в один метод ViewModel.

## Compose UI

- Composable-функции экранов принимают ViewModel и данные для отображения. Запрещено передавать в параметры экрана callback для обработки действий пользователя, событий экрана или навигации.
- Каждое действие пользователя и событие экрана передавай методу ViewModel, который обрабатывает его внутри Orbit `intent { ... }`. Если событие требует навигации или действия на уровне флоу, ViewModel отправляет `FlowEvent` через `FlowEventSink`, а решение принимает модуль routing.
- Внутренние UI-компоненты могут принимать обработчики, которые делегируют действие соответствующему методу ViewModel.

- Для отступов используй `VSpacer`, `HSpacer` и `WSpacer` из `ru.sla.pure.android.uikit.spacer`. При сравнении экрана с макетом применяй [чек-лист Compose UI](.agents/skills/compose-ui-review/SKILL.md).
- Источник Figma пока открыт. При каждом новом запросе с упоминанием Figma, пока подходящая ссылка отсутствует, напомни об этом и предложи варианты «A — добавить ссылку» и «B — пропустить». Пропуск относится к текущей задаче. Подробности и параметры сравнения заданы в чек-листе.
- Для доступа к Studio используй [Android CLI](.agents/skills/android-studio-cli/SKILL.md).
