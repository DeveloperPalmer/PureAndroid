# Обновление зависимостей

Применяй при обновлении и ревью обновлений библиотек, Android SDK, BOM, плагинов, Gradle Wrapper и JDK. Все команды Gradle ниже запускай по явной просьбе в соответствии с [правилами проекта](../code-quality/SKILL.md).

## Подготовка

1. Проверь доступные стабильные и предварительные версии по метаданным Google Maven, Maven Central, Gradle Plugin Portal или официальным релизам Gradle, JDK и Android SDK. Сверь целевую версию с запросом и требованиями совместимости проекта.
2. Изучи release notes и руководства по миграции для всех версий между текущей и целевой. Проверь изменения API и поведения, требования Android, Kotlin, AGP, Gradle и JDK, изменения манифестов, правил R8, транзитивных зависимостей и BOM.
3. Найди объявления и потребителей в [каталоге версий](../../../gradle/libs.versions.toml), [настройках сборки](../../../settings.gradle.kts), [Gradle Wrapper](../../../gradle/wrapper/gradle-wrapper.properties), файлах модулей и тестов. Включённая сборка [`build-conventions`](../../../build-conventions/settings.gradle.kts) использует тот же каталог и берёт из него версии плагинов для своих [зависимостей](../../../build-conventions/build.gradle.kts).

## Сравнение графов

1. Сохрани полные разрешённые графы до и после обновления. Используй Gradle Wrapper каждой ревизии и одинаковые параметры. Используй один JDK, если это допускают обе ревизии и цель обновления. Зафиксируй необходимые различия в окружении, включая JDK и SDK. Если обновление уже внесено, сними исходный граф в отдельной рабочей копии нужной ревизии.
2. Сравни compile и runtime classpath для Debug и Release затронутых Android-модулей. Включи `:app`, если изменение попадает в приложение, и конфигурации затронутых JVM-модулей, локальных тестов, инструментальных тестов, `testFixtures` и `build-conventions`. Используй `resolvableConfigurations`, чтобы найти доступные конфигурации каждого модуля.
3. Разбери каждый добавленный, удалённый или изменившийся компонент. Для общих библиотек используй `dependencyInsight`, чтобы найти пути зависимостей и ограничения BOM, повлиявшие на выбор версии. При необходимости проверь опубликованные Gradle Module Metadata и POM. Записи `FAILED` считай ошибками разрешения, даже если Gradle завершил задачу успешно. Для большого графа можно снять машиночитаемый снимок через `ResolutionResult` во временном init script и проверить `UnresolvedDependencyResult`.
4. Каталог задаёт запрошенные версии, а итоговые выбирает Gradle. Если обновление транзитивно подняло явно объявленную версию, согласуй соответствующий ключ каталога с требованиями графа, включая связанные тестовые артефакты. Отдельно отметь расхождения, которые существовали до обновления. Версии библиотек под Compose BOM меняй через BOM. Сверяй координаты `group:artifact` перед выравниванием. Избегай несвязанных обновлений и `force`, `strictly` или исключений, скрывающих требования зависимостей. После правок каталога разреши граф повторно и разбери все дополнительные изменения.

Команды ниже рассчитаны на запуск в PowerShell из корня репозитория.

```powershell
.\gradlew.bat :app:resolvableConfigurations
.\gradlew.bat :app:dependencies --configuration releaseRuntimeClasspath
.\gradlew.bat :app:dependencyInsight --configuration releaseRuntimeClasspath --dependency androidx.compose
.\gradlew.bat :app:dependencyInsight --configuration releaseRuntimeClasspath --dependency com.squareup.okhttp3
.\gradlew.bat :build-conventions:dependencies --configuration runtimeClasspath
```

Повтори отчёты для остальных затронутых конфигураций и модулей.

## Проверка и ревью

- Скомпилируй затронутых потребителей и проверь требования AAR metadata и дубли классов. При изменении R8 запусти реальную минификацию Release с применимыми keep rules, чтобы проверить оптимизацию и обфускацию. В [конвенции приложения](../../../build-conventions/src/main/kotlin/android-application-convention.gradle.kts) оптимизация Release сейчас выключена, поэтому для такой проверки временно включи её в отдельной рабочей копии.
- При изменении разрешений или компонентов проверь итоговые merged manifests. Удаляй временные обходы только после подтверждения, что исправление в новой версии покрывает исходный сценарий.
- Подбери регрессионные сценарии по затронутому поведению. Для сети и Paging проверь обработку ошибок, повтор запроса и догрузку страниц, для Navigation 3 проверь возврат с экрана деталей. Изменения Compose проверяй на затронутых экранах с поддерживаемыми темами, крупным шрифтом и TalkBack. Для проверок на устройстве используй подходящие инструментальные UI- или E2E-тесты проекта. Полный регресс запускай по отдельной просьбе.
- В отчёте укажи объявленные и разрешённые версии до и после, причины выбора версий, команды и результаты проверок, а также оставшиеся проверки. На ревью отмечай скрытые транзитивные изменения, расхождения с каталогом, пропущенные шаги миграции и риски для поведения, в том числе при обновлении одной строки.
