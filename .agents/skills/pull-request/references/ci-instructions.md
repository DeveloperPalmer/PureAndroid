# GitHub Actions и Gradle

Основа — [.github/workflows/ci-pull-request.yml](../../../../.github/workflows/ci-pull-request.yml), [конвенции](../../../../build-conventions/src/main/kotlin) и [правила качества](../../code-quality/SKILL.md). Текущий workflow запускается для PR в `main`; `test` зависит от `validation` через `needs`. Проверяй фактические команды и настройки выбранной ревизии.

- Проверь `on`, ветки, paths-фильтры, glob и `if`: нужные изменения не должны пропускать обязательные проверки, лишние пути — запускать несвязанные задачи без причины.
- Проверь `needs`, условия выполнения после ошибки и передачу artifacts между jobs. Условия и `continue-on-error` должны соответствовать обязательности проверки; не делай обязательную проверку необязательной для получения зелёного статуса.
- Для публикаций/релизов проверь требуемый триггер и согласование через workflow/environment. Не добавляй возможность релиза из обычного PR.
- Проверь минимальные `permissions`, использование secrets и недоверенного кода PR, особенно при `pull_request_target`. Не вставляй title/body/branch из события в shell как исполняемый текст; исключи утечки секретов в логах и artifacts.
- Cache keys должны учитывать входы и окружение, влияющие на совместимость; проверь риск загрязнения кэша. Для artifacts проверь paths, потребителей и retention, для длительных jobs — `timeout-minutes`.
- Сверь JDK runner, Kotlin JVM target, Android SDK, AGP и Wrapper по требованиям затронутых версий. Не требуй, чтобы номер JDK обязательно совпадал с JVM target.
- Проверь применение конвенций, зависимости слоёв, различия Debug/Release, testFixtures и сгенерированные исходники. Сохраняй воспроизводимость задач и не объявляй результаты форматирования/анализа по одному чтению diff.
- Для изменений версий применяй [dependency-upgrades](../../dependency-upgrades/SKILL.md). Для запуска Gradle через CLI, IDE или workflow требуется явная просьба на соответствующую операцию; само ревью такого разрешения не даёт.
