# Подготовка pull request

Применяй при подготовке описания и создании PR в PureAndroid. Заголовок пиши на английском, описание — на русском. Ветки и коммиты оформляй на английском.

## Содержание

- Заголовок кратко описывает результат изменения и содержит ровно один платформенный тег `[android]`. Без задачи: `[android] Add profile logout`. При реальной связанной GitHub Issue: `[#123][android] Fix profile logout`; для нескольких задач перечисли их номера перед тегом. Это соглашение PureAndroid, адаптированное из Karandash omim. Не придумывай номера: текущая работа может выполняться без задач.
- Заголовок коммита использует тот же формат и не превышает 72 символов. Тело объясняет существенную причину изменения, когда это необходимо. Реальные задачи, указанные в коммитах PR, должны быть представлены в его заголовке и ссылках описания. Правило применяется к новым коммитам; переписывание опубликованной истории требует отдельной просьбы.
- `CHANGELOG` в PR и коммитах не требуется. При AI-помощи добавь в конец описания `AI: <модель или -->` и `Skill: <фактически использованный skill или -->`. Эти поля фиксируют происхождение, а не требуют определённого провайдера; не выдумывай название модели.
- Начни описание с решённой проблемы и нового поведения. Для небольшого изменения достаточно одного-двух предложений и результатов проверки.
- Если есть связанная задача, добавь её реальную ссылку в Markdown.
- Укажи выполненные проверки и их результаты. Для отложенных проверок укажи причину и необходимые команды. При изменении UI добавь доступные скриншоты, если они помогают оценить изменение.
- Запуск Gradle и тестов регулируют [правила проекта](../../code-quality/SKILL.md). Для обновления зависимостей также примени [правило обновлений](../../dependency-upgrades/SKILL.md).

Основа описания, которую нужно заполнить по фактическому diff и проверкам.

```markdown
## Изменения

<Проблема, новое поведение и причина выбранного решения.>
<Ссылки на реальные связанные задачи, если они есть.>

## Проверка

<Выполненные проверки и их результаты.>
<Отложенные проверки: причины, команды и ожидаемые сценарии.>

AI: <модель или -->
Skill: <использованный skill или -->
```

## Состав коммита и служебные файлы

- Планы, отчёты агента, черновики PR и другие вспомогательные материалы конкретной задачи не входят в результат изменения и не публикуются в репозитории. Храни их вне рабочего дерева, например в `$env:TEMP`; описание и результаты проверок размещай непосредственно в PR. Постоянную документацию проекта добавляй только по явной задаче разработчика.
- Перед staging проверь каждый изменённый и новый файл. Добавляй только файлы результата задачи, затем проверь `git diff --cached --name-status` и полный staged diff. Не считай файл частью задачи только потому, что он создан агентом или находится в `docs/`; массовое добавление каталога не заменяет эту проверку.
- Перед push проверь полный список файлов относительно целевой ветки, включая ранее закоммиченные изменения: служебный файл может уже находиться в истории текущего PR. Проверь и описание PR на ссылки на исключённые файлы. `.gitignore` не исключает уже отслеживаемые файлы; удаляй их из итогового diff. Переписывай опубликованную историю только по отдельной явной просьбе.

## Создание через GitHub CLI

1. Проверь `gh --version` и `gh auth status --hostname github.com`. Продолжай через CLI после успешного выполнения обеих команд.
2. Проверь репозиторий, текущую ветку, её коммиты и полный diff относительно целевой ветки. Для PureAndroid целевая ветка по умолчанию — `main`, на неё настроен [CI](../../../../.github/workflows/ci-pull-request.yml). Учитывай явно указанную пользователем целевую ветку.
3. Проверь публикацию ветки и наличие уже открытого PR для неё. При повторной работе обнови существующий PR.
4. Получи список доступных labels через `gh label list --repo DeveloperPalmer/PureAndroid --limit 1000`. Если список достиг лимита, увеличь лимит, чтобы увидеть все метки. Выбирай метки по их реальному названию и описанию, области изменений и типу работы. Добавь все явно подходящие метки, включая метку AI-помощи, если такая существует и применима. Если подходящих меток нет, отметь это в итоговом сообщении. Ошибку получения списка сообщи как ограничение проверки меток.
5. Сохрани готовое описание в UTF-8 во временный файл вне рабочего дерева (например, в `$env:TEMP`) и передай его через `--body-file`. Для каждой выбранной метки добавь `--label '<точное имя>'`. Назначь текущего GitHub-пользователя через `--assignee '@me'`.

Пример команды для PowerShell с заполнителями для ветки, заголовка и файла описания.

```powershell
gh pr create --repo DeveloperPalmer/PureAndroid --base main --head '<branch>' --title '<title>' --body-file '<absolute-path-to-body.md>' --assignee '@me'
```

После создания проверь заголовок, описание, ветки, assignee и labels у полученного PR и верни его ссылку. Результаты CI сообщай по фактическому статусу проверок.

## Ручное создание

Если автоматическое создание недоступно, подготовь готовые заголовок и описание и дай ссылку сравнения опубликованной ветки. Для PureAndroid используй адрес вида `https://github.com/DeveloperPalmer/PureAndroid/compare/main...<branch>?expand=1`, заменив ветки фактическими значениями и закодировав специальные символы для URL. Укажи необходимые assignee и labels, если удалось получить их список.

Синтаксис команд описан в документации [gh pr create](https://cli.github.com/manual/gh_pr_create) и [gh label list](https://cli.github.com/manual/gh_label_list).
