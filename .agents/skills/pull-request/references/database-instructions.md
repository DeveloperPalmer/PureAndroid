# Room 3: данные и миграции

Проверяй [database](../../../../database), экспортированные схемы в `database/schemas`, настройки `room3`/KSP в build-файле и [DatabaseModule](../../../../app/data/src/main/kotlin/ru/sla/pure/android/app/data/di/DatabaseModule.kt). В проекте отдельные `characters.db` и `settings.db`, предоставляемые в `AppScope`.

## Схема и обновление приложения

- При изменении entity/схемы проверь версию `@Database`, соответствие экспортированного JSON и путь миграции от поддерживаемых установленных версий до новой. Проверяй регистрацию миграций/auto migrations в реальном builder; не предполагай, что существующие миграции уже есть.
- Сравни старую и новую схему: nullability, SQL-типы, default, PK, FK, индексы и преобразование существующих строк. Новая обязательная колонка должна получить корректное значение для старых данных.
- Изменение имени файла БД, destructive fallback, удаление таблиц или пересоздание хранилища требуют явного намерения потерять соответствующие данные. `IF EXISTS` само по себе не защищает от потери данных.
- Проверяй SQL на SQLite, доступном через выбранный драйвер и поддерживаемые Android-версии. Не объявляй все CREATE/DROP/переименования запрещёнными: оцени безопасное копирование данных, порядок DDL/DML, ограничения и транзакцию. Не переносись на номера файлов `.sqm`.
- Рассматривай повреждённые и частично заполненные данные, обновление существующей установки и повторное открытие БД. При отсутствии выполненной проверки миграции сообщай ограничение, а не успешность по одному JSON.

## DAO и конвертеры

- Согласуй запросы, параметры, сущности и domain: PK/уникальность, nullability, отсутствующие строки и порядок результатов. `IN` не гарантирует порядок входных ID — проверь восстановление порядка в `CharacterDao.readPage`.
- Проверь `@Transaction` для связанных операций. В `savePage` данные персонажей и список ID страницы должны сохраняться согласованно; очистка при завершении сессии не должна оставлять несогласованные потребительские данные.
- Оцени `@Upsert` и конфликтные стратегии по семантике. `REPLACE` может удалить и вставить строку заново; учитывай каскады и идентичность строки, если они есть.
- Проверяй индексы по условиям запросов, связям и ожидаемому объёму. Отсутствие индекса без сценария замедления не является самостоятельным дефектом.
- Для `@ColumnTypeConverter` проверь регистрацию, симметрию encode/decode, пустые значения, разделители, повреждённый формат и совместимость со старыми строками. Не подменяй ошибки разбора произвольным нулём, если это меняет данные.
- Для потоков результатов и `@DaoReturnTypeConverters` проверь преобразование и подписки на обновления; не требуй SQLDelight-адаптеров в конструкторе Room.

## Время жизни и потоки

Проверь application context, scope экземпляров, отсутствие конфликтующих имён файлов и использование правильного DAO. Пересоздание объекта БД само по себе не стирает файл — подтверждай фактическое последствие.

Проверяй блокирующие операции на Main. Не требуй `Dispatchers.IO` вокруг каждого suspend DAO/Flow без проверки его выполнения; учитывай настройки Room и реальный код конвертеров. Проверки Gradle и новые тесты требуют отдельной просьбы по AGENTS.md.
