# Проектирование изменения

Результат проектирования — решение, по которому разработчик может согласовать реализацию. Учитывай уже принятые решения и применимые инструкции репозитория. Обычное чтение кода само по себе не требует этого процесса.

## Задача и исходное поведение

- Сохрани формулировку разработчика. Уточни, кто пользуется результатом, какое поведение должно измениться и по какому наблюдаемому признаку можно принять работу.
- Проследи один репрезентативный сценарий от точки входа до результата. Найди владельца поведения, действующий контракт, его потребителей и существующие проверки. Расширяй поиск, когда обнаруженная зависимость влияет на решение.
- Для фактов, определяющих выбор, укажи проверяемый источник. Для поведения стороннего API укажи версию и документацию или исходник этой версии. Утверждения о деталях реализации сверяй с исходником. Если версия, нагрузка или состояние данных неизвестны, обозначь допущение и его влияние на выбор.
- Задай вопрос, когда ответ меняет контракт, объём работы или допустимый риск. Остальные обратимые допущения зафиксируй и продолжай.

## Выбор решения

Для локального обратимого изменения опиши один подход, его ограничение и проверку результата. Если есть несколько жизнеспособных подходов с разными последствиями, сравни их на одном сценарии. За исходную точку возьми текущее поведение. Укажи, при каком требовании или измерении предпочтительный вариант изменится.

Определи границу изменения и объясни, что увидят существующие потребители. При изменении API, состояния или формата данных используй [практики проектирования контрактов](references/api-canon.md). При дорогом откате проверь сценарий частичного внедрения и возможность восстановления. Для риска производительности задай условия измерения и допустимый результат. Оценки помечай как оценки.

Предложи последовательность работ с проверяемым результатом каждого шага. Укажи, какой сценарий подтверждает новое поведение и какой защищает прежний контракт. Для предложенных проверок назови окружение и ожидаемый результат. Отдельно обозначь уже выполненные проверки.

## Передача решения

Следуй формату запроса. Краткий выбор подхода можно обосновать в чате. Для полноценного плана по умолчанию подготовь [HTML-документ](references/document-style.html) вне рабочего дерева и верни ссылку. Включи цель и критерии приёмки, рекомендацию и её основания, существенные ограничения, шаги реализации и проверки. Добавляй разделы об альтернативах, зависимостях и открытых вопросах, когда они влияют на дальнейшую работу.

В HTML замени примеры и убери пустые разделы. Трекер имеет смысл, если по плану будут отмечать выполненные шаги. Для него задай уникальный `KEY` и сохраняй идентификаторы неизменившихся пунктов при обновлении документа. Отметки привязаны к браузеру. Проверь итоговый файл и ссылки. Передай документ на согласование. Реализация и внешняя публикация требуют соответствующего запроса разработчика.

## Применение в PureAndroid

Соблюдай [инструкции проекта](../../../AGENTS.md). Для поиска владельца поведения используй [карту проекта](../navigation-map/SKILL.md). При работе с экраном применяй соглашения Compose, Orbit и routing из инструкций проекта. Для сравнения с макетом используй [чек-лист UI](../compose-ui-review/SKILL.md).

Gradle, включая отчёты о зависимостях, запускай только по явной просьбе выполнить соответствующую операцию. Если вывод зависит от разрешённого classpath, используй доступный отчёт либо укажи точную команду для модуля и неподтверждённую версию. Новые тесты добавляй только по явной просьбе.
